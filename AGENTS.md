# Description
Small scope 2d world generator, simulation engine, rendering engine, algorithm runner for synthetic data generation, and algorithm assessment.
A small high performance C++ library for generating synthetic crop/field data for use in dataset generation, algorithm ground truthing, unit testing algorithms. 
Can render the world, to generate inputs for algorithms, and can do this entirely headlessly. The world should be able to handle millions of crops. 


# Archtitecture

## World
The world and its entities are entirely immutable. 

### Worldfile (binary representation)
The world can be snapshot-serialised into a binary representation that allows loading and reinstating the world exactly.

### World description (yaml)
This is a multilevel representation of the world. It could explicitly define each entity in the world down its lowest
level. This property means its very easy to quickly script small worlds for unit tests with a high level of control.
For example:

```yaml
seed: 568616        # generation should be deterministic 
label_name: {       # label_name can be whatever, just for organisation          
    objtype: 'Crop' # objects in the following list will instantiate a C++ Crop class, which will be instantiable from this description
    [
        {
            pos: [0.2, 1.03]
            leaves: [
                {type: 'ellipse', pos: [0.15, 0.0], rx: 0.15, ry : 0.05, theta: 1.3},   # internal leaf representation with ellipses
                {type: 'ellipse', pos: [0.0, 0.15], rx: 0.15, ry : 0.05, theta: 0.2},
                {type: 'ellipse', pos: [0.0, -0.15], rx: 0.15, ry : 0.05, theta: 0.2},
                {type: 'ellipse', pos: [-0.15, 0.0], rx: 0.15, ry : 0.05, theta: 1.0},
            ],
        },
        ...
    ]
}
```

There will also be generators, higher level descriptions that can directly generate objects. For example this generator describes a high, field level description.

``` yaml
other_label_name: {
    gentype: 'FieldGen',
    [
        {
            bounds: [[0.0, 0.0], [5.0, 0.0], [5.0, 5.0], [0.0, 5.0]],
            lines: [4, 8, 5],
            bedwidth: 2.0
            ...
        }
    ]    
}
```
The field generator will ultimately produce only Crop objects, but allows specifying at a higher level.
The world description is human readable, editable, and primary purpose is convenience. The worldfile on the other hand is to avoid recomputing the world (for large worlds). Both the high level and low level representation can be combined in the same description. 


### World Entities
These are represented by a C++ class. 
Entities should all support snapshot serialisation or instantiation from a YAML representation. 
This will also need to all be renderable. 
They will also have computed properties, not available in the world description, but will be reinstantiated after snapshot deserialisation.

### Generators
These are not world entities themselves (do not contribute to the world state / representation), they are parameterised convenience
classes / functions for creating world entities, or lower level generators, which ultimately populate the world. 


## Environment (Simulation Environment)
I'm terming the ambient space around the world the simulation environment. While the world is immutable, the environment is not. The environment
includes:
    - extrinsic state;
        - world identifier hash
        - current time
        - frame number
    
    - intrinsic state:
        - pose, velocity of each observer   
        - internal state of the algorithms run by each observer
        - algorithm output - the set of points generated by the algorithm after taking a step


### Environment file (binary)
The environment should be snapshot-serialisable and able to be deterministically recreated from a snapshot. The environment should be snapshot-deserialised independently of the world. 

## Observers
The only dynamic entity is an observer type. They cannot change the world, but can only affect their internal state. They can move around the world.
On each engine step, the observer can move, and then observe the environment (render what it can see), and then pass the observation to its attached algorithms, along with the world state, and the environments extrinsic state. 

### Algorithms
These can be attached to the observers, each will process the observers observation, and then will generate an output. 

## Critic
These can be attached to the algorithms, and will process the world state, the observer internal state, and the algorithm output, and will score each algorithm output on each step, or potentially even the agreggated algorithm output. 

## Engine 
This will step the environment, advancing the pose, and velocity of each observer. It will then call observe() on each observer. The observer will render what it can see (creating a transient observation ie: image ). Each algorithm attached to the observer will then process this observation, and will update their internal state. 
Step order: 
- timeadvancement
- movement 
- observation
- algorithm update
- scoring

## General considerations

Coordinate frames:
- x forward
- y left
- z up 

Camera coordinate frames:
- x - right (i image coordinate)
- y - down (j image coordinate)
- z - focal axis

Right hand rule rotations about their respective axis.
Use transforms / Quaternions. (Consider the Eigen c++ library for this)
Language standard: c++17+ compatibility
Unit tests using doctest (much faster than gtest, or ctest)
Only x86_64_linux is explicitly supported

C++ must be linted. Use CppCoreGuidelines style. 
Use a separate directory for tests.

Developing on nixos, ideally this project will be managed with a flake. Otherwise, it should still be a normal c++ library that other projects can include.

# Past milestones
Goal:
Introduce an internal generator subsystem under include/cropsim/generators and src/generators. All concrete generators derive from an abstract Generator interface and create crops through a shared deterministic generation context that owns PRNG state and entity-ID allocation. Add a factory that maps the YAML gentype value to built-in generator implementations. Extract the existing grid generation logic unchanged, keep generators out of world snapshots, and support explicit crops and generated crops in the same description.

Acceptance criteria:
  - The existing example generates byte-for-byte identical snapshots before and after the refactor.
  - Factory dispatch constructs the grid generator from gentype.
  - Unknown and missing gentype values are rejected.
  - Multiple generators receive unique sequential crop IDs and deterministic random values.
  - Explicit and generated crops coexist with stable ordering.
  - Invalid grid parameters and multiplication overflow are rejected.
  - A second test-only generator can be added without editing the world-building control flow, demonstrating that
    the abstraction actually removes the current type-specific branch.


Goal:
Add a deterministic, immutable uniform-grid spatial index to World. Index crops by their world-aligned extent
without changing crop IDs or canonical crop storage order. Expose deterministic AABB intersection queries and
update the renderer to use them. Serialize the index in a new snapshot version and validate it during
deserialization. Construction must remain linear in crop count for fixed density.

Acceptance criteria:
- world representation has includes the spatial index which can also be serialised deterministically
- spatial indexing / crop ordering is deterministic
- bench marking tests (in test suite) for both world creation and lookup reporting: lookup density, construction time, lookup latency, candidate count, and memory overhead.
    - world is simple square, density is kept the same
    - 50 Crops - small test size
    - 1000 Crops - short run
    - 1M Crops - single field size test 
    - 10M Crops - multi field test

Goal:
Use SDL Render/Graphics stack. CPU rendering is deterministic and is the source of truth. Viewing utility uses sped up GPU rendering, renders are approximate, not the source of truth. Support terminal rendering in so that unit tests can print images to terminal in case of failure. Nix derivation for viewer.

# Current milestone

Goal:
Separate crop placement from crop geometry generation. Placement generators decide where crops exist; crop generators independently create their immutable, ordered leaf geometry. Implement a deterministic generic rosette crop generator.

Architecture:
- Replace the generic generator API with typed `PlacementGenerator`, `CropGenerator`, and corresponding factories collected in a `GeneratorRegistry`.
- Placement generators receive the crop-generator factory and invoke the selected crop generator once per crop.
- Crop generators return `std::vector<EllipseLeaf>` and do not assign world positions or entity IDs.
- Retain the global placement PRNG and sequential ID allocator.
- Derive an independent morphology PRNG from the world seed, crop ID, and a fixed domain tag, so crop geometry changes cannot affect placement jitter.
- Register built-in `fixed` and `generic` crop generators. Generators remain transient and are excluded from snapshots.

YAML and compatibility:
- Compose placement and crop generation with a nested `crop` mapping under each grid generator.
- Scale and leaf parameters accept distributions; scale is sampled once per crop. Scalar distribution values are fixed. Missing mapping members use documented defaults, and omitted `stddev` defaults to `(max - min) / 6`.
- Preserve grid-level `radius` and `leaves` as shorthand for the fixed crop generator, but reject nested crop geometry combined with either shorthand.
- Keep explicit low-level crops supported and do not change snapshot v3. Legacy grid YAML must remain byte-identical.
- Generate generic leaves in index order with the leaf-length major axis (`radius_x`) pointing radially along `theta`, and the leaf-width minor axis (`radius_y`) perpendicular to it.
- Use bounded truncated-Gaussian rejection sampling with SplitMix and Box-Muller, failing after 10,000 rejected samples.
- Validate finite ordered ranges, means within bounds, standard deviations, positive scale/length/width/count, and non-negative minimum radial placement.
- Update the README and the ten-crop viewer example to demonstrate grid/generic composition.

Acceptance criteria:
- Generic crops regenerate deterministically with exact leaf ordering.
- Swapping fixed, generic, or injected crop generators does not alter positions, jitter, or IDs.
- Split and combined grids preserve current deterministic placement behavior.
- A test-only crop generator plugs into the grid without changing grid or world-building control flow.
- Tests cover default, structured, and scalar parameters; generated bounds; geometry formulas; independent random streams; registration and dispatch; legacy snapshot identity; and invalid configurations.
- Missing or unknown crop generators, ambiguous geometry, invalid distributions, and exhausted sampling are rejected.
- The library, viewer and shaders, complete test suite, and benchmark target build successfully.
